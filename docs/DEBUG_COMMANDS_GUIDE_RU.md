# USB-протокол управления весами v1

Команды реализованы в прошивке, 13 октября 2026 года. WiFi/OTA удалены.
Кнопки и интеграция в отдельно разрабатываемое приложение описаны в [текстовой инструкции](CLIENT_APP_INSTRUCTIONS_RU.txt).
[Анализ исходной версии](CODE_ANALYSIS_RU.md) относится к состоянию до этой доработки.

## Транспорт и форматы

115200 baud, 8N1, ASCII, LF или CRLF. Один запрос — одна строка, до **95 байт**
без окончания строки. ID — десятичное число 1…65535. Команды регистронезависимы,
числа с точкой. Пустые строки игнорируются.

```text
@<id> <COMMAND> [arguments]
#R <id> OK [key=value ...] done=1
#R <id> ERR <ERROR_CODE> done=1
#E <job_id> <EVENT> error=<code|NONE> [key=value ...]
```

HELP и STATUS возвращают **две строки**:
`part=1 done=0`, затем `part=2 done=1`. Клиент должен собрать обе строки.
`done=1` завершает ответ на запрос; завершение тары/калибровки подтверждается
событием, а не начальным `accepted=1`. В строках нет текстов с пробелами внутри значения.

`job_id` — ID запроса TARE или CAL START. Все этапы данной калибровки и её финальное
событие относятся к этому ID. Подтверждения CAL ZERO/LOAD/APPLY/CANCEL имеют свои ID.
Системные события используют job_id=0.

Обычный поток веса остаётся `123.45 S\n`. Строки `#R` и `#E` разбираются отдельно.
Без команд служебные события не добавляются к обычному потоку; первый корректно
оформленный командный frame активирует отладочные события до перезапуска.
Старый складской клиент должен пропускать служебные строки либо использовать отдельный
отладочный сеанс с STREAM OFF. Исходников прежнего клиентского приложения в этом
репозитории нет.

## Команды и кнопки

| Команда | Назначение | Завершение |
|---|---|---|
| HELP | Возможности и технические пределы | Две строки ответа |
| STATUS | Режим, датчик, вес, настройки, boot ID | Две строки ответа |
| GET FACTOR | Коэффициент, source, dirty | Ответ |
| GET RAW | Последний absolute ADC, offset, net, age_ms, seq | Ответ; без повторного чтения |
| TARE | Свежая устойчивая тара контейнера/платформы | ACK, затем TARE_DONE или TARE_FAILED |
| SET FACTOR value | Изменить делитель в RAM | Ответ; ноль не меняется |
| SAVE | Сохранить действующий factor в NVS | Ответ saved=1; unchanged=1 при отсутствии изменений |
| LOAD | Восстановить сохранённый factor | Ответ loaded=1; ноль не меняется |
| AUTO_TARE ON/OFF | Включить/выключить отслеживание нуля | Ответ; RAM |
| STREAM ON/OFF | Включить/выключить строки веса | Ответ; диагностика продолжает работать |
| CAL START grams | Начать калибровку с эталоном | ACK, состояние CAL_WAIT_ZERO |
| CAL ZERO | Подтвердить пустую платформу | ACK, затем CAL_WAIT_LOAD |
| CAL LOAD | Подтвердить установленный эталон | ACK, затем CAL_REVIEW или CAL_FAILED |
| CAL STATUS | Этап, job, reference, samples, spread, candidate, result | Ответ |
| CAL APPLY | Применить candidate factor и измеренный ноль | ACK и CAL_DONE; NVS отдельно |
| CAL CANCEL | Отменить активную калибровку | ACK и CAL_CANCELLED |

HELP/STATUS/GET/CAL STATUS/STREAM доступны в любом режиме. Новые TARE/CAL START
требуют завершённого запуска и исправного датчика. SET/LOAD/SAVE/AUTO_TARE запрещены
во время старта, тары и активной калибровки; при SENSOR_ERROR изменение настроек
остаётся доступным. CAL ZERO/LOAD/APPLY допускаются только в своём этапе.
CAL CANCEL доступна во всех пяти CAL-состояниях, включая sampling и review.
Прежний однобуквенный запуск `c` не поддерживается.

## Поля статуса

| Поле | Смысл |
|---|---|
| state | BOOT_WAIT_SENSOR, WEIGHING, TARING, CAL_WAIT_ZERO, CAL_ZERO_SAMPLING, CAL_WAIT_LOAD, CAL_LOAD_SAMPLING, CAL_REVIEW, SENSOR_ERROR |
| sensor | STARTING, OK, SENSOR_TIMEOUT, ADC_RANGE |
| has_sample | Получен ли хотя бы один ADC |
| valid | Можно ли использовать вес сейчас; при 0 игнорировать weight и stable |
| weight | Отфильтрованный вывод в граммах, с прежним порогом пустоты 10 г |
| raw_weight | Нефильтрованный нетто-вес в граммах |
| empty, stable | Признаки пустоты и стабильности; stable=0 при valid=0 |
| age_ms, seq | Возраст последнего ADC и номер отсчёта |
| job, result | Последняя/активная операция; RUNNING, OK, CANCELLED или код ошибки |
| factor | Действующий коэффициент, отсчётов ADC на грамм; используется как делитель |
| source | DEFAULT, NVS, MANUAL или CALIBRATION |
| dirty | Действующий factor отличается от сохранённого или сохранённого нет |
| auto_tare, stream | Текущие переключатели |
| boot | Восьмизначный hex ID данного запуска; изменение означает reboot |
| protocol | Версия протокола, сейчас 1 |
| boot_config | Результат загрузки коэффициента при старте |
| dropped | Пропущенные/отозванные строки веса при TX-нагрузке или потере валидности |

GET RAW возвращает `adc` (абсолютный ADC), `offset`, `net=adc+offset`,
`valid`, `has_sample`, `age_ms`, `seq`.
При has_sample=0 числовые поля ADC не возвращаются. Последний ADC может быть
устаревшим; ориентируйтесь на valid/age_ms.

`S` означает окно из восьми отфильтрованных измерений с разбросом менее 1 г.
Это не подтверждение точности калибровки. Номинальная частота вывода — 10 Гц;
при занятой линии строки веса могут пропускаться.

## Тара и автоматический ноль

При старте ADC читается непрерывно, первые 500 мс пропускаются для установления,
затем собираются 16 устойчивых отсчётов. Груз при включении становится частью
стартового нуля, поэтому запускайте устройство с пустой платформой.
При отсутствии/шуме ADC диагностика доступна, числовой поток приостановлен.

TARE пропускает первые 400 мс после запроса, собирает окно из 16 свежих absolute ADC,
принимает среднее за ноль и очищает фильтр/стабильность. Исходный offset сохраняется
до успешного завершения. При ошибке offset не меняется. Ручная тара не пишет NVS.

После успешной TARE автотара остаётся **выключенной**, чтобы не потерять тару
контейнера. При снятии контейнера допустим отрицательный нетто-вес.

Автотара при каждом включении устройства выключена. При AUTO_TARE ON она отслеживает
только устойчивые свежие мгновенные значения в пределах ±0.5 г, удерживающиеся
10 секунд. Вес 20 г не обнуляется по запаздывающему EMA. Нагрузка внутри диапазона
автонуля может быть принята за дрейф: программно отличить её от дрейфа невозможно.
Во время ручных операций автоматический ноль отключён; при отказе/отмене возвращается
прежняя политика, при успешной таре/калибровке остаётся выключенным.

## Калибровка

```text
@20 CAL START 275
#R 20 OK accepted=1 state=CAL_WAIT_ZERO job=20 dirty=... done=1
[убрать груз]
@21 CAL ZERO
#R 21 OK accepted=1 state=CAL_ZERO_SAMPLING job=20 ... done=1
#E 20 CAL_WAIT_LOAD error=NONE samples=16 ...
[поставить эталон 275 г]
@22 CAL LOAD
#R 22 OK accepted=1 state=CAL_LOAD_SAMPLING job=20 ... done=1
#E 20 CAL_REVIEW error=NONE samples=16 ... factor=-120 ...
@23 CAL APPLY
#R 23 OK accepted=1 state=WEIGHING job=20 dirty=1 done=1
#E 20 CAL_DONE error=NONE ... factor=-120 auto_tare=0
@24 SAVE
#R 24 OK factor=-120 dirty=0 saved=1 unchanged=0 done=1
```

Многоточия обозначают дополнительные поля, фактический поток их не содержит.

Расчёт: `factor = (mean_load_adc - mean_zero_adc) / reference_grams`,
`offset = -round(mean_zero_adc)`. Суммы 64-битные.
До CAL APPLY оба действующих параметра остаются прежними. Кандидат не сохраняется
автоматически. CAL CANCEL и ошибка отбрасывают кандидат без изменения действующего
масштаба и нуля.

На выборку даётся 5 секунд (включая установление 400 мс); окно — 16 значений,
максимальный разброс — 240 ADC counts. Минимальный полезный сигнал эталона —
64 counts и не менее четырёх текущих разбросов. Ожидание пользователя и review —
до 60 секунд на этап. Нестабильное окно сдвигается до устойчивого либо deadline.
В режиме TARING/CAL обычный вес не передаётся, RX/TX и STATUS работают.

## Числовые пределы и настройки

В config.h заданы технические пределы:
`0.01 <= abs(factor) <= 1000000`, `1 <= reference_grams <= 100000`.
Это пределы ввода, **не паспортная грузоподъёмность**. Диапазон эталона,
шумовой допуск и порог пустоты нужно настроить по конкретной механике весов.
HELP сообщает фактические пределы прошивки.

Отрицательный factor допустим. 0, NaN/Inf, переполнение/underflow, запятая вместо
точки и числовой токен с мусором отвергаются. SET FACTOR/LOAD очищают фильтр и
окно стабильности, но не тарируют груз.

NVS namespace/key сохранены: `vesy/cal_factor`. Проверяется результат putFloat.
SAVE выполняет синхронную запись flash; её нельзя запускать во время sampling.
Ошибка SAVE не отменяет RAM-настройку, но dirty остаётся 1. LOAD сначала валидирует
временное значение; неудача не заменяет действующий factor.
При отсутствии/ошибке сохранённого значения на старте используется default
и причина доступна через boot_config. SAVE сохраняет только factor, без offset,
stream и auto_tare. Без SAVE ручной factor исчезнет после reboot.

## Ошибки и повтор запросов

Коды: BAD_FRAME, UNKNOWN_COMMAND, INVALID_ARGUMENT, OUT_OF_RANGE, LINE_TOO_LONG,
BUSY, INVALID_STATE, SENSOR_TIMEOUT, ADC_RANGE, UNSTABLE, SIGNAL_TOO_SMALL,
USER_TIMEOUT, NVS_OPEN_FAILED, NVS_WRITE_FAILED, NO_SAVED_FACTOR,
INVALID_SAVED_FACTOR, ID_CONFLICT, INTERNAL_ERROR. ERROR события — поле error.

Строка длиннее лимита/с управляющими символами отбрасывается до LF;
её хвост не выполняется как команда. Незавершённый frame получает timeout после
1 с без нового байта. Повреждённый/переполненный frame даже после timeout остаётся
в discard до LF. При невозможности разобрать ID используется ответ ID=0.

Последние **8** обработанных ID/запросов/ответов кешируются до **30 секунд**.
Активный ID TARE/CAL START удерживается сверх TTL/оборота кэша до окончания
операции. Повтор ID с тем же нормализованным запросом повторяет исходный ACK/ERR,
не запускает действие; другой запрос с таким ID получает ID_CONFLICT.
Ошибочный ответ тоже кешируется, поэтому после исправления ошибки используйте новый ID.

За пределами окна/кэша и после reboot защита от повторного действия не гарантируется.
Клиентское приложение не должно повторять мутации автоматически после timeout; следует запросить STATUS.
При потере ACK результат можно выяснить через STATUS/CAL STATUS и job/result.
Меняйте ID для каждого нового действия, не используйте один постоянный ID кнопки.
Boot ID позволяет обнаружить перезапуск, но не является долговечным журналом операций.

## Датчик, очередь и клиент

Timeout готовности ADC — 1000 мс. При timeout/насыщении (16 counts от крайних
значений 24-битного диапазона) снимается valid/S, операция завершается ошибкой.
После восстановления собирается новое окно; имеющаяся ручная тара сохраняется.
Если стартовая тара ещё не завершилась, после восстановления она повторяется.

Готовность DT не является полной аппаратной диагностикой: обрыв с ложным ready
может дать правдоподобные цифры. Точность и реальные отключения проверяются на плате.

В TX — ограниченная очередь, ответы имеют приоритет перед ещё не начатой строкой
веса. Часть начатой строки всегда дописывается перед следующей. Мутация выполняется
только при наличии места для ответа; при перегрузке RX dispatch ждёт свободный TX.
Клиент должен отправлять последовательно, дожидаясь done=1. UART не сообщает,
прочитал ли приложение данные на ПК; подтверждение доставки требует чтения ответов.

Реализация: config, device, operations, commands, protocol.
Единственный вызов sensor.read находится в device.cpp; HTTP/WiFi в сборке нет.
Native-тесты проверяют реальный C++ с mock ADC/UART/NVS/временем; это не замена
аппаратной проверке коэффициента, шума и USB-UART моста.
