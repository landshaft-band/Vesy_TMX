ИНСТРУКЦИЯ ДЛЯ ДРУГОГО ДИАЛОГА: УПРАВЛЕНИЕ ВЕСАМИ В СУЩЕСТВУЮЩЕМ ПРИЛОЖЕНИИ
Прошивка ESP32/HX711, USB-протокол v1. Актуально на 13 октября 2026 года.
Кодировка файла: UTF-8. Документ самодостаточный, готового кода приложения не содержит.

1. ЗАДАЧА И ГРАНИЦЫ РАБОТЫ

В другом диалоге разрабатывается существующее клиентское приложение на Python/PyQt.
Оно уже получает массу от ESP32 через USB COM-порт. Нужно дополнить это приложение
отдельным разделом «Управление весами», сохранив существующий рабочий интерфейс.
Использовать код, архитектуру и версию PyQt существующего приложения. Не создавать
вместо него новое приложение, не менять прошивку и не добавлять WiFi/HTTP/OTA.

Прошивка уже реализует все описанные ниже команды. В проекте прошивки не требуется
создавать клиентский код. Реализацию кнопок и клиентского обмена выполнить в проекте
приложения, используя эту инструкцию как контракт с устройством.

Основные требования:
- прежний поток массы продолжает обслуживать складскую часть приложения;
- один COM-порт открывается и читается одним транспортным worker;
- тот же worker принимает ответы команд и события операций;
- операции и ожидание ответов не блокируют GUI;
- ACK означает подтверждение запроса, а не обязательно завершение операции;
- состояние кнопок определяется реальным состоянием весов;
- старый вес не считается достоверным при отсутствии данных/активной операции.

2. ПОРТ И СОВМЕСТИМОСТЬ

Транспорт: USB-UART мост ESP32. Скорость 115200 baud, 8 бит данных, без чётности,
1 стоп-бит (8N1). Аппаратное управление потоком прошивкой не настроено.
COM4 — настройка одного ПК, не постоянный адрес устройства: использовать порт,
выбранный в существующем приложении. Закрывать Serial Monitor перед подключением.

Прежняя строка массы сохранена:
123.45 S
-12.34 U
0.00 S

Единица — грамм. Десятичный разделитель — точка, знак минус допустим.
S — маленький разброс в окне измерений, U — нестабильность/незаполненное окно.
Номинальная частота — 10 строк в секунду. Строки могут повторять один отсчёт
или пропускаться при нагрузке TX; не считать каждую строку обязательно новым ADC.

Без отправки команд прошивка не добавляет в этот поток отладочные события.
После начала управления в том же порту появятся строки #R и #E. Поэтому перед
подключением кнопок обязательно дополнить существующий parser различением строк:
масса; ответ команды; событие операции; неизвестная/диагностическая строка.
Нельзя передавать #R/#E в прежний числовой parser массы.

Поток не идёт во время стартовой тары, ручной тары, калибровки и отказа датчика.
После включения устойчивый стартовый ноль обычно собирается около 2 секунд при
10 SPS. Платформа должна быть пустой: груз при включении станет частью нуля.
Автотара после каждого включения выключена, поток массы включён.
Сохраняется только калибровочный коэффициент; тара и переключатели не сохраняются.

3. ФОРМАТ ЗАПРОСОВ

Каждый запрос — одна ASCII-строка:
@<id> <COMMAND> [arguments]

Обязательно дописать настоящий байт LF (0x0A). Допустим CRLF (0x0D, 0x0A).
Обозначение \n в документации — один байт LF, а не два символа «\» и «n».
Максимум 95 байт содержимого без окончания строки. Пустые строки игнорируются.
Команды регистронезависимы; рекомендуется всегда отправлять верхний регистр.
Числовые аргументы передавать с точкой, независимо от локали GUI.

ID — десятичное целое 1…65535. Для каждого нового действия выдавать новый ID.
Это касается и повторных нажатий одной кнопки. Не закреплять постоянный ID за кнопкой.
Не переиспользовать ID активной операции или ещё актуального запроса.

Примеры запросов (номера здесь только иллюстрируют формат):
@101 STATUS
@102 TARE
@103 SET FACTOR -120.5
@104 SAVE
@105 CAL START 275

4. ФОРМАТ ОТВЕТОВ И СОБЫТИЙ

Успех запроса:
#R <id> OK <key=value ...> done=1

Ошибка запроса:
#R <id> ERR <ERROR_CODE> done=1

Событие операции:
#E <job_id> <EVENT_NAME> error=<code|NONE> <key=value ...>

Поле ID связывает #R с конкретным запросом. job_id связывает #E с длительной
операцией: это ID команды TARE или CAL START, а не ID очередного CAL ZERO/LOAD.
Каждая команда CAL ZERO/LOAD/APPLY/CANCEL получает собственный ID и собственный #R;
события всех этапов данной калибровки продолжают использовать ID её CAL START.
Системные события используют job_id=0. Ответ #R с ID=0 означает, что ID входного
frame разобрать не удалось; не назначать его произвольному ожидающему запросу.

Все дополнительные поля — разделённые пробелами key=value; значения без пробелов.
Не привязываться к порядку полей. Разбирать только известные поля и сохранять
возможность пропускать новые. Числовые поля проверять перед использованием.

HELP и STATUS возвращают две строки с одним ID:
#R <id> OK ... part=1 done=0
#R <id> OK ... part=2 done=1

Собрать поля обеих строк. Запрос завершён только после done=1 или явного ERR.
Не считать part=1 отдельным завершённым STATUS и не разрешать управление до
получения всего начального статуса. У обычного одночастного ответа part может
отсутствовать. На некорректную последовательность частей реагировать как на
повреждённый ответ, не объявлять запрос успешно выполненным.

Ключевое различие:
- done=1: ответ на запрос завершён;
- accepted=1: действие принято/запущено;
- TARE_DONE/CAL_DONE: длительная операция успешно завершилась.

В частности, TARE получает быстрый ACK и отдельный финальный #E позже.
CAL ZERO/LOAD получают ACK перед сбором выборки. CAL APPLY тоже возвращает
accepted=1; успешное применение подтверждается CAL_DONE и обновлённым STATUS.

5. СПИСОК ВСЕХ КНОПОК И СООТВЕТСТВУЮЩИХ КОМАНД

5.1. «Команды / возможности» -> HELP
Показать версию протокола, список возможностей и ограничения ввода. Ответ состоит
из двух частей. Перечень commands в HELP содержит условные имена вида GET_FACTOR;
это НЕ буквальные команды. Отправлять GET FACTOR с пробелом, как указано здесь.

5.2. «Обновить статус» -> STATUS
Получить полный статус, показать режим, датчик, массу, коэффициент, dirty,
автотару и поток. Ответ состоит из двух частей. Этой же командой выполнять
фоновый опрос, примерно раз в 500 мс; не накапливать одинаковые запросы.

5.3. «Прочитать коэффициент» -> GET FACTOR
Ответ содержит factor, source, dirty, done=1. Обновить отображение действующего
коэффициента. Не затирать незавершённый пользовательский ввод в поле редактирования.

5.4. «Сырые отсчёты» -> GET RAW
Показать adc, offset, net, возраст и номер отсчёта. Это диагностика последнего
прочитанного значения; команда не заставляет HX711 сделать новый отсчёт.
Если has_sample=0, полей adc/offset/net нет. При valid=0 отображать их как
устаревшую диагностику, не использовать для обычного достоверного веса.

5.5. «Тарировать» -> TARE
Назначение: ноль для пустой платформы либо контейнера. На ACK показать
«Тарирование выполняется», заблокировать конфликтующие действия. Дождаться
TARE_DONE либо TARE_FAILED. До успешной выборки offset остаётся прежним.
При успехе обновить STATUS, сбросить старую стабильность и показать auto_tare=0.
Тара не пишет NVS. Снятие тарированного контейнера может дать отрицательную массу.
Отдельной команды отмены TARE в протоколе нет; сбор ограничен сроком 5 секунд.

5.6. «Установить коэффициент» -> SET FACTOR <value>
Взять числовое значение из поля ввода и отправить с точкой. Коэффициент может
быть отрицательным. Он является ДЕЛИТЕЛЕМ, в единицах ADC counts на грамм.
Команда меняет только RAM, не тарирует груз. После ACK обновить действующий
коэффициент и dirty; предложить отдельное сохранение. Фильтр/стабильность сброшены,
поэтому прежний S больше не действителен до новой выборки.

5.7. «Сохранить в весах» -> SAVE
Сохранить действующий factor в NVS ESP32. Успех содержит saved=1, dirty=0.
При unchanged=1 запись не требовалась: значение уже сохранено.
Сохранение не следует выполнять автоматически на каждом опросе или каждом
изменении поля GUI. При ошибке factor в RAM может продолжать действовать;
не показывать «сохранено» без успешного ответа.

5.8. «Загрузить сохранённый» -> LOAD
Восстановить factor из NVS в RAM, не меняя offset. Успех содержит loaded=1,
factor, dirty=0. Фильтр и стабильность сбрасываются.
При NO_SAVED_FACTOR/INVALID_SAVED_FACTOR действующий factor не заменяется.
Показать причину; не изображать загрузку default как успешный LOAD.

5.9. Переключатель «Автоматический ноль» -> AUTO_TARE ON / AUTO_TARE OFF
После ACK и STATUS синхронизировать положение переключателя с устройством.
Не отправлять команду при программном обновлении checkbox из статуса.
Автоноль при старте выключен. При включении допускает устойчивую коррекцию
в пределах ±0.5 г после выдержки 10 секунд. Малый постоянный груз внутри этого
диапазона программно неотличим от дрейфа. Ручная тара/успешная калибровка оставляют
автоноль выключенным; отмена/отказ возвращают прежнюю политику.

5.10. Переключатель «Передавать поток веса» -> STREAM ON / STREAM OFF
Переключает только обычные строки массы. Ответы/события и STATUS продолжают
работать. После STREAM OFF уже начатая строка может ещё прийти: parser обязан
корректно обработать её. Переключатель синхронизировать по ACK/STATUS, не по
предположению об успешной отправке байтов.

5.11. «Начать калибровку» -> CAL START <grams>
Передать массу эталона из отдельного поля ввода в граммах. После ACK сохранить
job_id и перейти к экрану/подсказке освобождения платформы. Не начинать следующую
стадию автоматически: пользователь должен подтвердить пустую платформу.

5.12. «Подтвердить ноль» -> CAL ZERO
Доступна только в CAL_WAIT_ZERO. Пользователь сначала убирает груз, затем нажимает
кнопку. ACK переводит в CAL_ZERO_SAMPLING. Ждать события CAL_WAIT_LOAD.

5.13. «Эталон установлен» -> CAL LOAD
Доступна только в CAL_WAIT_LOAD. Пользователь устанавливает эталон с массой,
заданной в CAL START, затем подтверждает. ACK переводит в CAL_LOAD_SAMPLING.
Ждать CAL_REVIEW либо CAL_FAILED. Не путать эту команду с отдельной командой LOAD,
которая загружает коэффициент из NVS.

5.14. «Статус калибровки» -> CAL STATUS
Показать state, job, reference, samples, spread, candidate, result.
Для прогресса активной операции можно опрашивать дополнительно примерно раз
в секунду, объединяя повторные запросы. Поле spread — разброс ADC counts,
а не граммов. Точный remaining_ms прошивкой не возвращается.

5.15. «Применить калибровку» -> CAL APPLY
Доступна только в CAL_REVIEW. До нажатия показать рассчитанный candidate как
ПРЕДЛАГАЕМЫЙ factor отдельно от действующего. Команда применяет candidate и
измеренный zero offset одновременно, но не сохраняет factor в NVS.
После CAL_DONE обновить STATUS и дать возможность нажать SAVE.

5.16. «Отменить калибровку» -> CAL CANCEL
Доступна во всех пяти CAL-состояниях, в том числе во время сбора и review.
Получить ACK и CAL_CANCELLED с исходным job_id. В этом событии error=CANCELLED —
нормальная отмена пользователем, а не ошибка записи/датчика.
Прежние действующие factor/offset остаются. Обычный поток возобновляется при
исправном датчике. Не отправлять CAL APPLY после отмены.

6. ПОЛЯ STATUS И ДИАГНОСТИКИ

Первая часть STATUS:
state — BOOT_WAIT_SENSOR, WEIGHING, TARING, CAL_WAIT_ZERO, CAL_ZERO_SAMPLING,
        CAL_WAIT_LOAD, CAL_LOAD_SAMPLING, CAL_REVIEW или SENSOR_ERROR.
sensor — STARTING, OK, SENSOR_TIMEOUT или ADC_RANGE.
has_sample — 0/1: получен ли хотя бы один ADC.
valid — 0/1: можно ли сейчас использовать вес.
weight — отфильтрованный вывод массы в граммах.
raw_weight — нефильтрованная масса, также в граммах.
empty — 0/1: отфильтрованный вес находится в зоне пустоты.
stable — 0/1; при valid=0 трактовать как недействующий.
age_ms — возраст последнего ADC, НЕ таймер стадии калибровки.
seq — номер прочитанного отсчёта ADC.
job — ID последней/активной операции.
result — NONE, RUNNING, OK, CANCELLED либо код ошибки операции.
part=1 done=0.

Вторая часть STATUS:
factor — действующий factor.
source — DEFAULT, NVS, MANUAL или CALIBRATION.
dirty — 1: factor отличается от сохранённого либо сохранённого нет.
auto_tare — 0/1.
stream — 0/1.
dropped — число пропущенных/отозванных обычных строк массы.
boot — восьмизначный hex ID данного запуска ESP32.
protocol — сейчас 1.
boot_config — результат загрузки NVS при запуске.
part=2 done=1.

boot_config=NO_SAVED_FACTOR/INVALID_SAVED_FACTOR/NVS_OPEN_FAILED при старте не
обязательно означает отсутствие массы: прошивка использует валидный default
(приблизительно -118.217293). Показать источник/причину отдельно от sensor/valid.
source описывает происхождение действующего factor; после SAVE может остаться
MANUAL/CALIBRATION. Признак сохранения — dirty=0 и успешный SAVE, не source=NVS.

GET RAW: adc — абсолютный ADC; offset — текущее смещение; net=adc+offset.
Формула массы до фильтра: raw_weight=net/factor.
Порог пустоты сохранён: при abs(filtered_weight)<10 г вывод weight равен 0.
raw_weight не имеет этого обнуления. Не менять граммы на килограммы в передаче;
если GUI использует килограммы, преобразовывать только отображение.

7. ПРАВИЛА ДОСТУПНОСТИ КНОПОК

Нет соединения/не подтверждён протокол: запретить мутации. Разрешить подключение
и диагностическую проверку STATUS/HELP. Первым получить полный STATUS,
убедиться в protocol=1, запомнить boot и текущие настройки.

WEIGHING:
- TARE и CAL START разрешены при исправном/свежем датчике;
- SET FACTOR, SAVE, LOAD, AUTO_TARE разрешены;
- CAL ZERO/LOAD/APPLY/CANCEL запрещены, если калибровка не активна;
- диагностика и STREAM доступны.

BOOT_WAIT_SENSOR или TARING:
- запретить новые TARE/CAL START, SET FACTOR/SAVE/LOAD/AUTO_TARE;
- оставить диагностику и STREAM;
- в TARING показать ожидание результата, не объявлять устройство отключённым
  только из-за паузы обычного потока.

CAL_WAIT_ZERO: разрешить CAL ZERO и CAL CANCEL.
CAL_ZERO_SAMPLING: из управляющих стадией оставить CAL CANCEL.
CAL_WAIT_LOAD: разрешить CAL LOAD и CAL CANCEL.
CAL_LOAD_SAMPLING: из управляющих стадией оставить CAL CANCEL.
CAL_REVIEW: разрешить CAL APPLY и CAL CANCEL.
Во всех CAL-состояниях запретить TARE, новый CAL START, SET FACTOR, SAVE, LOAD,
AUTO_TARE; диагностика/STREAM остаются доступными.

SENSOR_ERROR:
- масса недостоверна, TARE/CAL START не разрешать;
- прошивка позволяет SET FACTOR/SAVE/LOAD/AUTO_TARE;
- диагностика/STREAM доступны.

Пока ожидается ACK управляющего запроса, исключить повторное нажатие конфликтующих
кнопок. После ACK длительной операции не разблокировать всё до её завершения.
Сначала обновить состояние из ответа/события/STATUS. Нельзя включать кнопки
по одному только локальному таймеру. При BUSY/INVALID_STATE запросить статус,
не пытаться насильно менять состояние прошивки.

8. СОБЫТИЯ, КОТОРЫЕ НУЖНО ОБРАБОТАТЬ

TARE_DONE — успешная тара.
TARE_FAILED — отказ тары, причина в error.
CAL_WAIT_LOAD — нулевая выборка готова, можно установить эталон.
CAL_REVIEW — эталон измерен; поле factor содержит кандидат, ещё не применённый.
CAL_DONE — калибровка применена в RAM.
CAL_CANCELLED — отмена, прежние параметры сохранены.
CAL_FAILED — ошибка/timeout калибровки.
BOOT_DONE — стартовая тара готова, системный job_id=0.
BOOT_FAILED — стартовая выборка не удалась, системный job_id=0.
SENSOR_ERROR — отказ/недостоверность ADC, системный job_id=0.
SENSOR_RECOVERED — данные восстановились после завершённого старта, job_id=0.

События содержат error, samples, spread, offset, factor, auto_tare.
Для CAL_REVIEW factor — кандидат. Для остальных событий это действующий factor
на момент формирования события. Не переносить candidate из CAL_REVIEW в поле
действующего коэффициента до CAL APPLY/CAL_DONE.
События принимать независимо от ожидаемого #R: они могут прийти между его частями.
Старое событие другого job не должно завершать текущую операцию.
После финала/восстановления обновить полный STATUS. Не запускать никаких действий
автоматически в ответ на BOOT_DONE/SENSOR_RECOVERED.

9. АРХИТЕКТУРА ОБМЕНА В СУЩЕСТВУЮЩЕМ ПРИЛОЖЕНИИ

Использовать уже существующий COM-worker; дополнить его очередью записи, если
раньше он только читал массу. Не открывать ещё один Serial для раздела управления.
Чтение/запись с ограниченными timeout выполнять в фоне. В GUI доставлять данные
через Qt signals; ожидание ACK/этапа организовать через состояния и таймеры.
Не блокировать слот кнопки ожиданием readline, sleep или while до завершения.

Входящие байты накапливать до LF: один read может принести половину строки или
несколько строк сразу. Удалять только завершающий CR для CRLF. Ограничить буфер
строки, например 1024 байт; при переполнении отбрасывать до LF. Неизвестные строки
(включая возможный лог ROM при включении) отправлять в лог, а не в массу.

Отправлять запросы последовательно, максимум один незавершённый #R-запрос.
Следующий запрос отправлять после done=1/ERR. Длительная операция не держит
этот слот после ACK: во время её выполнения можно запрашивать STATUS/CAL STATUS.
Ограничить очередь, объединять повторные диагностические опросы, не заливать
UART множеством ожидающих STATUS. Пользовательская отмена не должна ждать
длинной очереди фоновых запросов.

Хранить ID, команду, время отправки, части ответа и назначение запроса.
Обрабатывать ответы по ID, не по предположению «следующая строка — мой ответ».
Поздний ответ после timeout не назначать новому запросу.
Логировать исходящие команды, #R/#E, ошибки/перезапуски; журнал сделать ограниченным.

Периодически получать STATUS даже при STREAM ON, чтобы знать valid и boot.
STREAM OFF не означает неисправность: при valid=1 вес можно получать через STATUS.
Если STATUS.valid=0, отображать «—/нет достоверных данных», снять стабильность,
не использовать прежнюю массу в складских действиях. На TARING/CAL это ожидаемая
пауза измерения, при SENSOR_TIMEOUT/ADC_RANGE — ошибка датчика.
Если перестали приходить и ответы STATUS, признать состояние неизвестным,
очистить показ старой стабильной массы и заблокировать мутации.

10. TIMEOUT, ПОВТОРЫ, ПЕРЕЗАПУСК И ПЕРЕПОДКЛЮЧЕНИЕ

Ожидание ACK разумно ограничить 3 секундами. Это не deadline всей калибровки.
Тара/выборка: прошивке даётся до 5 секунд, обычно около 2 секунд при 10 SPS.
Приложение должно ждать финальное событие с небольшим запасом, например до
7–10 секунд, затем выяснять результат по STATUS, не повторять операцию вслепую.
Ожидание пользователя и review ограничены 60 секундами на этап. Можно показывать
приблизительный отсчёт, если приложение видело начало этапа; точного остатка
времени после позднего подключения прошивка не сообщает.

Прошивка хранит последние 8 ID/запросов/ответов до 30 секунд. Активный ID TARE
или CAL START удерживается сверх TTL/оборота кэша до завершения операции.
Повтор того же ID и нормализованного запроса возвращает исходный ACK/ERR,
не повторяет действие. Другой запрос с тем же ID возвращает ID_CONFLICT.
Ошибки также кешируются: исправленный новый запрос должен иметь новый ID.

За пределами TTL/кэша и после reboot повторное действие не исключено.
Поэтому не делать автоматический retry TARE/SET/SAVE/LOAD/AUTO_TARE/CAL после
потери/повреждения ответа. Очистить неотправленную очередь мутаций, заблокировать
управление до следующего достоверного STATUS, показать «исход команды неизвестен».
Сопоставить STATUS.job/result и CAL STATUS с сохранённым job_id. Для длительной
операции RUNNING означает продолжение, OK — завершение, код ошибки — отказ.
Если идентификатор операции/запуска уже другой, не объявлять старое действие
успешным по одному только совпадению factor или показанию массы.

При каждом переподключении выполнить свежий полный STATUS, не восстанавливать
автотару/поток/незавершённую калибровку автоматически. Если boot изменился,
считать ESP32 перезапущенной: очистить очередь, части ответов, активные ожидания
и прежнюю стабильность, принять фактические RAM-настройки из нового статуса.
Сохранённый factor может восстановиться, но ручная тара/переключатели — нет.
Boot ID не является постоянным уникальным серийным номером устройства.

DTR/RTS могут перезапускать ESP32 при открытии порта в зависимости от моста/драйвера.
Использовать согласованную политику существующего worker и проверить на плате;
не менять эти линии при каждом нажатии кнопки.

11. ЧИСЛОВОЙ ВВОД И СОХРАНЕНИЕ

Допустимые технические значения текущей прошивки:
0.01 <= abs(factor) <= 1000000; отрицательный factor разрешён, ноль запрещён.
1 <= reference_grams <= 100000.
Эти пределы не являются паспортной грузоподъёмностью весов. Реальное ограничение
эталона в приложении согласовать с конкретной механикой; не считать 100000 г
разрешённой физической нагрузкой только потому, что число проходит parser.
HELP сообщает фактические числовые пределы прошивки.

Проверять конечность числа, диапазон, пустой ввод и полный разбор значения.
Не отправлять NaN, Inf, переполнение/underflow и текст вроде «118abc».
Локализованный ввод с запятой сначала преобразовать в числовое значение, а затем
сформировать аргумент с точкой. Коэффициент показывать с достаточной точностью
(ориентир: 9 значащих цифр float32), не обрезать отрицательный знак.

Разделить в интерфейсе: действующий factor; редактируемое значение; candidate
калибровки; сохранённость dirty. Фоновый STATUS не должен стирать введённый,
но ещё не отправленный factor. Не объявлять поле сохранённым при SET/CAL APPLY.
SAVE сохраняет только factor в namespace/key vesy/cal_factor.
LOAD/SAVE не сохраняют/не загружают текущую тару контейнера.

12. ОШИБКИ И ПОНЯТНЫЕ СООБЩЕНИЯ

BAD_FRAME — неверный формат/ID/повреждённый frame.
UNKNOWN_COMMAND — команда не поддерживается.
INVALID_ARGUMENT — отсутствует/лишний/нечисловой аргумент.
OUT_OF_RANGE — число вне технического диапазона.
LINE_TOO_LONG — содержимое строки длиннее 95 байт.
BUSY — действие конфликтует с текущей операцией/недоставленным переходом.
INVALID_STATE — команда этапа не соответствует текущему состоянию.
SENSOR_TIMEOUT — нет достаточно свежих отсчётов/выборка не набрана в срок.
ADC_RANGE — сигнал около насыщения ADC.
UNSTABLE — устойчивое окно не получено в срок.
SIGNAL_TOO_SMALL — эталон не даёт достаточной разницы с нулём.
USER_TIMEOUT — истёк срок ожидания подтверждения/применения.
NVS_OPEN_FAILED — ошибка открытия хранилища ESP32.
NVS_WRITE_FAILED — factor не удалось сохранить.
NO_SAVED_FACTOR — сохранённого factor нет.
INVALID_SAVED_FACTOR — сохранённый factor невалиден.
ID_CONFLICT — ID уже использован другим запросом.
INTERNAL_ERROR — внутренний сбой форматирования ответа.

Для BUSY/INVALID_STATE обновить статус и доступность кнопок. Для ошибки входа
подсветить поле. Для ошибки датчика снять достоверность массы. Для ошибки NVS
показать, что RAM-настройка может действовать, но сохранение не выполнено.
При CAL_FAILED/TARE_FAILED сохранить на экране прежние действующие параметры
после проверки STATUS. Не применять candidate автоматически после отказа.
Не заменять отказ сообщением об успехе только из-за отсутствия исключения записи
на стороне ПК: успешный write в COM не означает исполнения команды.

13. ПРИМЕР ПОЛНОГО СЕАНСА КАЛИБРОВКИ

Числа иллюстративны. Все строки передачи заканчиваются LF. Дополнительные поля
ответов ниже приведены в действующем формате, их значения зависят от устройства.

ПК: @201 CAL START 275
ESP32: #R 201 OK accepted=1 state=CAL_WAIT_ZERO job=201 dirty=1 done=1
Интерфейс: «Освободите платформу. Подтвердите ноль».

Пользователь убирает груз и нажимает подтверждение.
ПК: @202 CAL ZERO
ESP32: #R 202 OK accepted=1 state=CAL_ZERO_SAMPLING job=201 dirty=1 done=1
ESP32: #E 201 CAL_WAIT_LOAD error=NONE samples=16 spread=0 offset=-1000 factor=-120 auto_tare=0
Интерфейс: «Установите эталон 275 г».

Пользователь устанавливает эталон и подтверждает.
ПК: @203 CAL LOAD
ESP32: #R 203 OK accepted=1 state=CAL_LOAD_SAMPLING job=201 dirty=1 done=1
ESP32: #E 201 CAL_REVIEW error=NONE samples=16 spread=0 offset=-1000 factor=-120 auto_tare=0
Интерфейс: отдельное поле candidate=-120; разрешена кнопка применения.

ПК: @204 CAL APPLY
ESP32: #R 204 OK accepted=1 state=WEIGHING job=201 dirty=1 done=1
ESP32: #E 201 CAL_DONE error=NONE samples=16 spread=0 offset=-1000 factor=-120 auto_tare=0
Интерфейс: результат применён, ещё не сохранён.

ПК: @205 SAVE
ESP32: #R 205 OK factor=-120 dirty=0 saved=1 unchanged=0 done=1
Интерфейс: «Коэффициент сохранён в весах».

Если вместо применения пользователь нажал отмену:
ПК: @206 CAL CANCEL
ESP32: #R 206 OK accepted=1 state=WEIGHING job=201 dirty=1 done=1
ESP32: #E 201 CAL_CANCELLED error=CANCELLED samples=16 spread=0 offset=-1000 factor=-120 auto_tare=0
Этот альтернативный ответ возможен только при ещё активной калибровке,
а не после CAL APPLY из предыдущей ветки.

14. ПРИМЕР STATUS

ПК: @301 STATUS
ESP32: #R 301 OK state=WEIGHING sensor=OK has_sample=1 valid=1 weight=123.45 raw_weight=123.45 empty=0 stable=1 age_ms=10 seq=90 job=0 result=OK part=1 done=0
ESP32: #R 301 OK factor=-120 source=MANUAL dirty=1 auto_tare=0 stream=1 dropped=0 boot=00000001 protocol=1 boot_config=OK part=2 done=1

Показать массу 123.45 г и стабильность только после проверки valid=1.
Коэффициент -120 действует в RAM и отличается от сохранённого (dirty=1).
В этом примере протокол подтверждён только после второй строки.

15. КРИТЕРИИ ПРИЁМКИ В ДРУГОМ ДИАЛОГЕ

1) Существующая складская часть получает прежние строки массы без ошибок #R/#E.
2) Один COM-reader обслуживает весь интерфейс; второй порт не открывается.
3) Все 16 перечисленных действий/групп кнопок доступны по соответствующим режимам.
4) STATUS/HELP собираются из двух частей; смешанные и фрагментированные данные
   читаются правильно, без зависания GUI.
5) ACK тары/калибровки не показывается как окончательный успех.
6) CAL проходит ZERO -> WAIT_LOAD -> LOAD -> REVIEW -> APPLY -> SAVE.
7) Отмена работает в каждом CAL-этапе, прежние настройки сохраняются.
8) SET/LOAD не тарируют находящийся груз; SAVE — отдельное действие.
9) Checkbox не отправляет команды при обновлении из STATUS.
10) Потеря ACK, неверный ID, поздний ответ, BUSY, повреждённая строка и отключение
    не приводят к автоматическому повтору мутации или использованию старого S.
11) После reboot очередь очищена, новые настройки взяты из реального STATUS.
12) Ошибка SAVE не отображается как успешное сохранение; dirty показывается честно.
13) Редактируемый factor не затирается фоновым опросом.
14) Проверены реальный USB-порт, пустой запуск, контейнерная тара, эталон,
    SAVE/reboot, отключение датчика и возвращение к обычному потоку массы.

Результат работы другого диалога — изменения в существующем приложении,
а не новая прошивка, не второй независимый клиент и не смена версии PyQt.
